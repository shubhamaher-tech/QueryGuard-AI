# Database Connection Security & Isolation Architecture

## 1. Principles of Operation

QueryGuard AI adheres to strict architectural isolation to protect production databases and sensitive customer records from unintended access or modification.

---

## 2. Connection Modes

```
+-------------------------------------------------------------------------+
| Mode 1: Local Sandbox Mode (ACTIVE & SAFE)                               |
| - Connects to isolated docker service `workload-postgres` (workload_db)  |
| - Read-only credentials: user `workload_ro`                             |
| - Safe test ground for synthetic e-commerce, TPC-H, and HypoPG           |
| - Zero customer records, credentials, or production data               |
+-------------------------------------------------------------------------+

+-------------------------------------------------------------------------+
| Mode 2: External Database Connection (SCAFFOLD ONLY — DISABLED)          |
| - Intentionally restricted and disabled in current build                 |
| - Protects production databases from accidental DDL or unverified queries|
| - UI displays an explicit security advisory explaining isolation policy |
+-------------------------------------------------------------------------+
```

### Mode 1: Local Sandbox Mode (Default & Active)
- **Host / Port:** `workload-postgres:5432` (internally) / `localhost:5433` (externally).
- **Target Database:** `workload_db`.
- **Telemetry User:** `workload_ro` (Read-only role with `GRANT SELECT ON pg_stat_statements`, `pg_read_all_stats`).
- **Enforced Settings:**
  ```sql
  SET TRANSACTION READ ONLY;
  SET statement_timeout = 10000;
  ```
- **Virtual HypoPG Simulation:**
  - Uses `hypopg_create_index()` exclusively inside transient backend sessions.
  - Virtual indexes exist in server RAM only; zero physical disk blocks are written.
  - Immediate cleanup via `hypopg_drop_index()` or automatic session rollback.

### Mode 2: External Database Scaffold (Disabled for Safety)
To prevent unauthorized production modifications or accidental data egress:
- The Settings UI provides the configuration scaffolding for future read-only production monitors.
- Attempts to activate external connections return a safety response:
  > *"External database connection mode is intentionally scaffolded and restricted to read-only simulation. To safeguard production environments from unauthorized modifications, QueryGuard AI defaults strictly to the local isolated workload-postgres container."*

---

## 3. Human Approval Gateway

QueryGuard AI **never** deploys schema modifications, creates physical indexes, or alters database configurations automatically:
1. Every recommendation generated by rule analysis or SLM rewrite requires explicit review by a DBA with role `DBA`.
2. Approving a recommendation generates a sanitized SQL migration script for review.
3. Every approval or rejection is immutably recorded in the QueryGuard audit trail (`audit_logs`) with actor attribution, timestamp, and policy flags (`NO_AUTOMATIC_PRODUCTION_DDL`).
